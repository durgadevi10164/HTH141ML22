# DMart SmartStock AI
### Inventory-Constrained Demand Forecasting & Smart Stock Allocation

> ⚠️ **DATA DISCLAIMER:** DMart branch-level sales and inventory data is proprietary and was **not** used anywhere in this project. Every dataset, number and figure in this application is **synthetic / simulated**, generated with a fixed random seed to produce realistic-looking retail demand patterns purely for hackathon demonstration purposes. This project is **not affiliated with or endorsed by** DMart / Avenue Supermarts Ltd.

---

## 1. Project Overview

DMart SmartStock AI is a full-stack, AI-powered retail inventory management demo. It simulates 5 supermarket branches around Coimbatore, 20 everyday SKUs, and a full year of daily sales history, then uses a trained machine learning model to forecast demand per branch/SKU and an inventory-constrained allocation engine to decide how a **limited** central warehouse should distribute stock across branches.

## 2. Problem Statement

Retail chains constantly face a mismatch between demand and available warehouse stock:
- Some branches run out of fast-moving items while others are overstocked.
- Festivals, weekends and promotions spike demand unpredictably.
- Warehouses can rarely fully satisfy every branch's requirement at once.

Without a data-driven system, allocation decisions are made manually or via simple equal-split rules that ignore real urgency and risk.

## 3. Solution

DMart SmartStock AI:
1. Forecasts per-branch, per-SKU demand for a chosen horizon (7 / 14 / 28 days) using a trained RandomForest regression model.
2. Compares forecast demand against current stock + a safety-stock buffer to compute the exact shortage per branch.
3. Runs a **priority-based allocation engine** that distributes a limited warehouse stock so the most urgent, highest-risk branches are served first — never exceeding the warehouse's available inventory.
4. Visualizes everything (KPIs, charts, risk levels, allocation tables) in a single interactive dashboard, with a "What-If" warehouse-stock simulator and a Peak Demand Monitor for festivals.

## 5. Features

- Synthetic dataset generator with realistic weekly/monthly/festival/promotion patterns (~36,500 rows).
- RandomForest demand-forecasting model with lag & rolling-mean features, trained and evaluated on the synthetic data (MAE/RMSE/MAPE reported, not faked).
- Inventory-constrained smart allocation engine with a transparent priority-score formula and per-branch allocation reasons.
- Stockout risk classification (LOW / MEDIUM / HIGH / CRITICAL).
- Interactive **Streamlit** dashboard: KPI cards, branch demand bar chart, historical-vs-forecast trend line chart, risk badges, allocation table, warehouse panel, and the highest-priority branch with an explanation.
- What-If warehouse-stock simulator (recalculates allocation live).
- Peak Demand Monitor: expected demand increase, top SKUs by demand jump and a recommended extra buffer per simulated festival, recalculated live from the dataset for the **selected branch / SKU** (or all).
- **Role-based login** (Branch / Inventory / Warehouse / Regional Supply Chain Manager) with server-side, role- and branch-scoped data - see *Login and roles* below.
- Demo Mode: sensible defaults (Rice 5kg, 7-day horizon, 5000-unit warehouse) load automatically on first open.
- Friendly error handling for missing files, invalid selections, and zero warehouse stock.
- Automated test suite (`tests/`) covering data quality, the forecast API, the allocation algorithm, and the warehouse-constraint invariant.

## 6. Dataset Explanation

Generated by `scripts/generate_data.py` with a fixed random seed (42) for reproducibility:

| File | Description |
|---|---|
| `data/branches.csv` | 5 simulated branches with a relative demand weight |
| `data/products.csv` | 20 SKUs across 5 categories with base price & base demand |
| `data/calendar.csv` | 365-day calendar with weekend/festival flags |
| `data/dmart_synthetic_sales.csv` | ~36,500 rows: date × branch × SKU daily sales & inventory |
| `data/inventory.csv` | Latest-date inventory snapshot with safety stock & reorder level per branch/SKU |

Patterns baked into the data: branch-level demand weighting, category-specific demand levels, weekly seasonality (weekend effects strongest for dairy/beverages/snacks), a mild monthly wave, 8 simulated festivals with category-specific demand boosts (Pongal, Republic Day, Tamil New Year, Independence Day, Navratri, Diwali, Christmas, New Year), randomized promotion bursts (~6% of days) with a demand lift, Gaussian noise, and inventory that logically restocks when it runs low. No negative sales or stock values are possible.

## 8. ML Model

- **Algorithm:** `RandomForestRegressor` (scikit-learn) — chosen for fast training, no extra native-build dependencies (unlike XGBoost/LightGBM), and strong performance on tabular retail data.
- **Features:** `lag_1/7/14/28`, `rolling_mean_7/14/28`, `day_of_week`, `month`, `weekend_flag`, `festival_flag`, `promotion`, `selling_price`, and encoded `branch`, `sku`, `category`.
- **Training:** `scripts/train_model.py` — an 80/20 train/test split, trained once on the full synthetic history.
- **Artifacts saved:** `models/demand_model.pkl` (model + category encodings + metrics), `models/metrics.json`.

### Reported evaluation metrics (computed on this project's synthetic test set — real numbers, not fabricated):

| Metric | Value |
|---|---|
| MAE | ≈ 3.17 units |
| RMSE | ≈ 4.79 units |
| MAPE | ≈ 13.7% |

(Exact values will vary slightly by machine/library version — rerun `scripts/train_model.py` to reproduce.)

## 9. Forecasting Methodology

For a chosen branch + SKU + horizon, the model performs a **recursive one-step-ahead forecast**: it predicts day 1, appends that prediction to the recent-history buffer, recomputes lag/rolling features, predicts day 2, and so on until the full horizon is covered. The sum of daily predictions is the total predicted demand for the period.

## 10. Allocation Methodology

For each branch, `shortage = (forecast_demand − current_stock) + safety_stock` (floored at 0). A **priority score** (0–100) is computed per branch:

```
priority_score = ( 0.5 × shortage_ratio
                  + 0.3 × min(stockout_urgency, 3) / 3
                  + 0.2 × min(demand_weight, 3) / 3 ) × 100
```

where `shortage_ratio = shortage / forecast_demand`, `stockout_urgency = shortage / current_stock`, and `demand_weight = forecast_demand / average_forecast_across_branches`. Branches are ranked by this score (ties broken by larger shortage) and the limited warehouse stock is handed out branch-by-branch in that order — each branch receiving `min(its shortage, remaining warehouse stock)`. This is **not** an equal split: high-urgency, high-risk, high-demand branches are served first, and the total allocated can never exceed the warehouse's available stock (enforced by an assertion and covered by automated tests).

## 11. Stockout-Risk Calculation

`coverage_ratio = current_stock / forecast_demand`:

| Coverage ratio | Risk |
|---|---|
| ≥ 1.0 | LOW |
| 0.6 – 1.0 | MEDIUM |
| 0.3 – 0.6 | HIGH |
| < 0.3 | CRITICAL |

## 14. Running the Project

The project has two processes: the **Flask backend** (JSON API on port 5000) and the **Streamlit dashboard** (port 8501), which calls the API.

**Easiest (Windows):** double-click `run.bat`, or run it from a terminal:

```bat
run.bat
```

This will (idempotently) create the virtual environment, install dependencies, generate the synthetic dataset, train the model, initialize the database, start the Flask backend in its own window, wait until the API answers, and then launch the Streamlit dashboard and open **http://localhost:8501** in your browser. Closing the dashboard (CTRL+C) also stops the Flask window that `run.bat` opened.

**Manual steps** (any OS) — use two terminals, both from the project root with the virtual environment activated:

```bash
# one-time setup
python -m venv venv
source venv/bin/activate        # venv\Scripts\activate on Windows
pip install -r requirements.txt
python scripts/generate_data.py
python scripts/train_model.py
python scripts/initialize_db.py

# terminal 1 - the API
python backend/app.py

# terminal 2 - the dashboard
streamlit run frontend_streamlit/app.py
```

Then open **http://localhost:8501** and log in (see *Login and roles*). (Opening http://127.0.0.1:5000 shows a small page pointing you to the dashboard; the API lives under `/api/...`.)

Run `streamlit` from the project root so the theme in `.streamlit/config.toml` is picked up.

### Login and roles

The dashboard opens on a **Login** page: choose a **Role** and enter your unique **Employee ID**. The backend checks that the ID belongs to the selected role (for example *Branch Manager + WM001* is rejected) and only then opens the role-specific dashboard. **Log out** is in the sidebar.

| Role | Demo Employee ID(s) | What the role sees |
|---|---|---|
| Branch Manager | `BM001` Singanallur, `BM002` Podanur, `BM003` Mettupalayam Road, `BM004` Chinniyampalayam, `BM005` Sulur | **Only their own branch**: stock, demand, shortage, stockout risk, recommended allocation, own-branch inventory and own-branch peak demand. The Branch filter is locked. Tabs: Overview, Allocation, Peak Demand Monitor |
| Inventory Manager | `IM001` | Inventory, demand, shortage and risk across **all branches / SKUs** (no warehouse allocation). Tabs: Overview, Inventory, Peak Demand Monitor, Model Performance |
| Warehouse / Distribution Manager | `WM001` | Warehouse stock, shortages and allocation (plus the What-If simulator). Tabs: Allocation, What-If Simulator, Peak Demand Monitor |
| Regional Supply Chain Manager | `RSM001` | The full chain-wide overview (all five original tabs) |

**Security model.** The role and branch come from a *server-side session* created at login (the client only holds an opaque bearer token), so the frontend cannot change them. Every API endpoint checks the role, and the data is filtered **in the backend** before it is returned (`backend/services/access_service.py`): a Branch Manager's dashboard, inventory, branch list, forecast and festival responses contain only their branch, and asking for another branch returns `403`. The role -> tabs/endpoints table lives in one place, `backend/services/auth_service.py` (`ROLES`). This is demo-grade authentication (fixed demo IDs, no passwords, in-memory sessions that expire after 8 hours or when the backend restarts) - replace `authenticate()` with a real identity provider before any real use. Set `DMART_SHOW_DEMO_IDS=0` to hide the demo-ID hint on the login page.

### Streamlit dashboard guide

(The tables below describe the full Regional Supply Chain Manager view; other roles see the subset listed above.)

| Area | What it shows | Source endpoint |
|---|---|---|
| Header + banner | Title and the "synthetic / simulated data" disclaimer | - |
| Filters | Branch, Category, SKU, Forecast horizon (7/14/28), Warehouse stock | `/api/branches`, `/api/products` |
| KPI cards | Total Branches, Total SKUs, Warehouse Stock, Predicted Demand, Potential Stockouts, Allocation Utilization | `/api/dashboard` |
| **Overview** tab | Branch demand bar chart, stockout-risk badges (LOW/MEDIUM/HIGH/CRITICAL), historical-vs-forecast trend | `/api/dashboard`, `/api/forecast` |
| **Allocation** tab | Warehouse panel, Highest Priority Branch card (with reason), allocation table (+ CSV download), current inventory | `/api/dashboard`, `/api/inventory` |
| **What-If Simulator** tab | Warehouse-stock slider; the backend re-runs the allocation and the tables/charts update | `/api/allocation` |
| **Inventory** tab (Inventory Manager) | Current / safety stock and reorder level for every branch and SKU | `/api/inventory` |
| **Peak Demand Monitor** tab | Festival demand uplift, top SKUs by demand jump, recommended extra buffer - for the **Branch filter** and a *SKU scope* switch (selected SKU / all SKUs) | `/api/festivals?branch_id=&sku_id=` |
| **Model Performance** tab | MAE / RMSE / MAPE from the trained model | `/api/metrics` |

Behaviour notes:

- **Branch filter:** the allocation is always computed chain-wide (the warehouse is shared), so choosing a branch only *focuses* the view: it highlights the bar, filters the allocation table, and switches the trend chart to that branch. The API exposes historical sales only for the highest-priority branch, so for any other branch the trend shows the forecast only (the app says so on screen).
- **Category filter** narrows the SKU dropdown.
- **What-If slider** covers 0 to about 1.5x the total requirement so the interesting range has good resolution.
- **Errors:** if the backend is not running, the dashboard shows a clear "Backend unavailable" message with the start command and a *Retry* button instead of crashing. If a single endpoint fails, only that section shows a warning while the rest keeps working.
- **Configuration:** the backend URL can be changed in the sidebar, or set with the `DMART_API_URL` environment variable (default `http://127.0.0.1:5000`).

## 15. API Documentation

All endpoints return JSON. Base URL: `http://127.0.0.1:5000`

Except for `/api/health` and `/api/auth/roles`, every endpoint needs a login token: call `POST /api/auth/login` and send the returned token as `Authorization: Bearer <token>`. Responses are `401` without a valid token and `403` if the role may not use the endpoint (or asks for another branch's data as a Branch Manager).

| Method | Endpoint | Description |
|---|---|---|
| GET | `/api/auth/roles` | Roles for the login form (public) |
| POST | `/api/auth/login` | `{ "role": "branch_manager", "employee_id": "BM002" }` -> `{ token, user, permissions }`; `401` if the ID does not belong to the role |
| GET | `/api/auth/me` | The signed-in user and permissions |
| POST | `/api/auth/logout` | Ends the session (the token stops working) |
| GET | `/api/branches` | List branches (Branch Manager: only their own) |
| GET | `/api/products` | List all SKUs + categories |
| GET | `/api/dashboard?sku_id=&horizon_days=&warehouse_stock=` | Dashboard payload (KPIs, charts, allocation, etc.), scoped to the caller's role |
| GET / POST | `/api/forecast` | Forecast demand for one branch + SKU + horizon (Branch Manager: own branch only; not for Warehouse Manager) |
| POST | `/api/allocation` | Run the allocation engine for one SKU across all branches (Warehouse / Regional managers) |
| GET | `/api/inventory?branch_id=&sku_id=` | Current inventory snapshot (Branch Manager: own branch only) |
| GET | `/api/metrics` | ML model evaluation metrics (Inventory / Regional managers) |
| GET | `/api/festivals?branch_id=&sku_id=` | Peak Demand Monitor, **recalculated from the sales history for the given branch / SKU** (omit either for "all"; Branch Manager: always their own branch) |
| GET | `/api/health` | Health check (public) |

Example — `POST /api/allocation`:
```json
{ "sku_id": "SKU001", "horizon_days": 7, "warehouse_stock": 1500 }
```

## 19. Limitations

- Data is synthetic; the model's real-world accuracy is untested.
- The recursive forecast doesn't know about *future* festivals/promotions the user hasn't configured (Demo assumes none unless the historical pattern already captured it through lag features).
- SQLite is single-file and fine for a demo, but not meant for concurrent production writes.
- Authentication is demo-grade: fixed demo Employee IDs, no passwords, in-memory sessions (a browser refresh or a backend restart means logging in again). This is a local hackathon demo, not a production system.
- Peak Demand Monitor: each festival is a single day in the synthetic data, so a very narrow selection (one branch + one SKU) rests on a single data point and the percentage can swing a lot; the tab says so.

## 20. Future Improvements
